Stock Monitoring & Low-Stock Alert System

📍 Jahra, Kuwait 🧪 Test data only 👆 Manual trigger 💰 Max spend 0 KD 🔔 Max 10 alerts per run

1 · Project Goal

“The agent checks the Jahra shop’s test inventory and flags products when their stock reaches or falls below the minimum stock level without changing inventory quantities.”

The agent is designed to detect low stock early, so that a human can decide whether more stock should be ordered. The decision always stays with the person.

🚫 The agent does NOT purchase products
🚫 The agent does NOT change inventory quantities
✅ The agent only identifies and records low-stock alerts

4 · Guardrails

The Rules the Agent Cannot Break

These four blocks are the most important part of the whole project. They describe what the agent must never do, when it must ask a human, what it is allowed to spend, and when it must stop completely.

🚫

NEVER

The agent must NEVER:

  • Change inventory quantities.
  • Purchase products.
  • Contact suppliers.
  • Invent a missing stock quantity.
  • Invent a minimum stock level.
  • Access inventory information outside the test data.
  • Use a tool that was not provided.
  • Expose passwords, API keys or credentials.
✋

ASK FIRST

The agent must ask a human before:

  • Changing any inventory information.
  • Sending information outside the test system.
  • Contacting a supplier.
  • Taking any purchasing action.
  • Handling unusual or conflicting inventory information.
💰

SPEND

Hard limits for every manual run:

0 KDMax spending per run
10Max low-stock alerts per run
The agent is not allowed to make purchases. Ordering stock is a human decision.
🛑

STOP AND ASK

The agent must stop and ask a human if:

  • Product name is missing.
  • Current quantity is missing.
  • Minimum stock level is missing.
  • Quantity contains invalid information.
  • Two inventory records conflict.
  • The agent cannot determine whether stock is low.
The agent must NEVER guess missing information.

5 · Stop Condition

END OF RUN
10Low-stock alerts per run
0 KDMaximum spending
HAND OVER If more than 10 products require alerts, the workflow stops and asks a human to review the remaining products.

⚠ The Rule That Changed

Rule 3 — Before, What Broke It, After

This is the heart of the project. The rehearsal found a real hole in the rule, so the rule was rewritten and then tested again.

Rule 3 — Before the rehearsal
“If current quantity is less than or equal to minimum stock, create a low-stock alert.”
↓
What broke it — Case 3 Juice Boxes

Juice Boxes had a minimum stock level of 8, but the current quantity field was empty.

The original rule did not explain how missing quantities should be handled.

If the empty value was treated as zero, the system could incorrectly create a low-stock alert — and a person could order stock that the shop does not actually need.

↓
Rule 3 — After
“If current quantity and minimum stock are both valid numbers, compare them. If current quantity is less than or equal to minimum stock, create a low-stock alert. If either value is missing or invalid, STOP and ask a human. Never treat missing information as zero.”

n8n Workflow

Five Nodes, Manual Trigger First

The workflow is deliberately small. It starts only when a person presses Execute Workflow, and it ends by writing to a test log — never to a supplier.

Node 1
👆 MANUAL TRIGGER
I press Execute Workflow. The agent never starts on its own.
Failure plan: Alert Human
Node 2
📄 READ TEST STOCK
Read product name, current quantity and minimum stock from the test sheet.
Failure plan: Retry ×3, 5 s apart → stop and alert human
Node 3
⚖️ CHECK STOCK LEVEL
Both values valid numbers? Then compare: current quantity ≤ minimum stock.
Failure plan: Alert Human / Stop Workflow — never assume missing means zero
IF LOW STOCK continue to Node 4
IF NOT LOW NO ACTION — run ends
Node 4
🔔 CREATE LOW-STOCK ALERT
Build the alert: product, current quantity, minimum stock, status, date/time.
Failure plan: Stop and Alert Human
Node 5
📝 SAVE ALERT TO TEST LOG
Write one row to the test alert sheet. Stop after 10 alerts in a run.
Failure plan: Retry ×3, 5 s apart → alert human

Failure Plans

Every Node Has a Plan for Going Wrong

A node that fails quietly is more dangerous than a node that stops loudly. Each node below says what happens when it fails.

Node 1
Manual Trigger
Alert Human
  • If the workflow cannot start correctly, no inventory check should happen.
Node 2
Read Test Stock
Retry
  • Maximum retries: 3
  • Wait: 5 seconds between retries
  • If it still fails: stop the workflow and alert a human
Node 3
Check Stock Level
Alert Human / Stop
  • If quantity or minimum stock is missing, DO NOT continue.
Never assume missing information means zero.
Node 4
Create Low-Stock Alert
Stop and Alert Human
  • Do not create an alert if required product information is missing.
Node 5
Save Alert
Retry
  • Maximum retries: 3
  • Wait: 5 seconds
  • If saving still fails: alert a human
Do not pretend the alert was successfully saved.

Final Reflection

What I Learned

What did the agent do well?

It correctly identified low-stock products using clear numerical rules.

What did the rehearsal break?

It exposed that the original rule did not explain what to do with missing stock quantities.

What rule changed?

The agent must now validate both numbers before comparing them.

When should the agent do nothing?

When stock is above the minimum level, or when required information is missing and human review is required.

What would need to change before automation?

The system would need secure credentials, stronger testing, error monitoring, approved inventory access, and clear human escalation procedures.
